# Mpv-infinity のビルド・公開

対象は `wim-web/Mpv-infinity`。作業場所とリモートを確認してから使う。
依頼された作業を進める。ビルドだけの依頼を、コミット・push・公開の依頼に拡大しない。

## ユーザーの方針

- 自分用。GitHubリリースのタイトルは **バージョン（タグ名）だけ** にする。
- リリース本文は **空文字**。変更説明、テスト件数、免責文、チェックサム、ビルド事情などを勝手に追加しない。
- 新たに説明を指定された場合だけ、その内容を書く。
- 成功時の返答も短く、リリースやAPKのリンクと結果を伝える。失敗・未検証事項を成功扱いにはしない。

## ビルド

- ホストにJavaやAndroid SDKがなくても、まずDockerを確認する。KotlinのビルドにはJDKが必要だが、ホストへの導入を前提に止まらない。
- 指定がなければ、動作確認用の `standard`・`arm64-v8a`・debug APK を作る。release署名や全ABIビルドは別途指示に従う。
- [Docker手順](references/docker.md)に、実際に成功した環境・コマンド・対処方法を記載している。SDKやツールのバージョンはその時点のリポジトリ設定に合わせる。
- 構文確認だけをビルド成功と呼ばない。GradleのAPK生成成功、単体テスト結果、生成APKの存在と署名を確認する。
- 既存APKのアップロード依頼なら、そのAPKを確認して使う。古い成果物を最新ソースのビルドと取り違えない。

## push・公開

- pushを依頼されたら、今回の変更をコミットし、対象ブランチとリモートを確認して通常のpushを行う。ビルド成果物や自動生成された無関係なファイルをコミットに含めない。
- 公開前に既存リリース・タグと対象コミットを確認する。バージョン指定があれば優先し、なければ現在のアプリバージョンと既存タグに合う未使用のタグを選ぶ。過去の `v2.1.5-library-preview.1` を毎回使い回さない。
- debug APK は既定でプレリリース、`--latest=false` とする。
- `gh release create` は `--repo wim-web/Mpv-infinity --target <対象SHA> --title <タグ名> --notes '' --prerelease --latest=false` とAPKを指定する。
- 既存リリースのタイトル・説明の訂正は `gh release edit` で行い、依頼されていないタグやAPKは差し替えない。
- 失敗や結果不明のときは、リリースとアセットの現在の状態を確認してから続行する。重複公開や無断の上書きをしない。
- 公開後は `isDraft=false`、タイトル、空の本文、アセットの `uploaded` 状態・サイズを確認する。GitHub側にdigestがあればローカルSHA-256と照合する。
